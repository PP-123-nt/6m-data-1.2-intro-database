Database Normalization: From Chaos to Clean

Introduction

The Update Anomaly Problem

Why do we need normalization? Let's see what happens when data is stored inefficiently.

Imagine a coffee shop that writes your complete home address on the paper slip every time you buy a coffee.

If you move house, they'd have to find every single coffee purchase you ever made and update your address.

This is called an Update Anomaly — changing one fact forces updates in many places.

Overview

The Three Normal Forms

Database normalization follows three progressive rules to eliminate redundancy.

Rule 1
1NF
“No Grocery Bags in Cells”
Two rules: (1) Each cell contains a single, atomic value — no comma-separated lists like "Apple, Banana, Pear". (2) Every row is uniquely identifiable, usually via a primary key. A table can pass rule 1 and still fail 1NF if rows aren't uniquely identifiable.
Rule 2
2NF
“The Address Book Rule”
Every column must depend on the entire primary key, not just part of it. Only matters when the key has more than one column (a composite key).
Rule 3
3NF
“The Phone Directory Principle”
No chain dependencies: no column should depend on another non-key column. Each fact depends only on the primary key.
Remember This Every fact should be about the key, the whole key, and nothing but the key. Let's apply these rules to a real e-commerce example!

FAQ
Why not just use (OrderID, ItemID) as the key instead of adding LineNumber?
In this sample data, (OrderID, ItemID) happens to be unique too — no order repeats the same item. But that only holds because of a business assumption: no order contains the same item twice. If a customer could add the same item to an order as two separate lines (e.g. different gift-wrap options), (OrderID, ItemID) would collide and 1NF would break again. LineNumber is a surrogate key — it identifies "the nth item on this order" regardless of what's in it, so it stays valid even if that business rule changes. This is why real order systems almost always use a surrogate line/row ID instead of building the key out of business data.
